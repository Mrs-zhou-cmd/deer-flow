# 前端流式解析与缓冲（Streaming Parsing & Buffers）

> 适用对象：想搞懂 DeerFlow 前端"流式响应"内部机制的开发者。
> 本文聚焦一件事：**SSE 字节流到达浏览器后，前端如何分层解析、缓冲、合并，最终渲染成流式回复**。
> 与 `chat-streaming-logic.md`（入门视角，讲完整链路）互补，本文是从"缓冲"这个横切面深入实现细节。
> 相关代码全部在 `frontend/src/`。

---

## 1. 缓冲区生命周期总览（何时进、何时清）

> 阅读导航：本节回答横切问题——**每个缓冲区什么时候开始进数据、什么时候被清空**。
> 机制细节在对应章节（表格最后一列标注），本节只给"进/清"边界和结论。

每个缓冲的生命周期都由 **三个边界** 驱动：

- **流开始** —— 进数据的起点：节流快照首帧立即渲染、重连游标写入、乐观消息入列
- **流结束** —— 正常清空点：节流快照置 `null`、乐观消息随服务器确认清除
- **异常事件** —— 强制清空点：`stream_replay_gap` / 错误 / 线程切换 → **全量清空**，防串台与陈旧残留

| 缓冲 | 进数据（何时开始） | 清空（结束 / 异常） | 详情 |
| --- | --- | --- | --- |
| 1. 字节解析缓冲 | 网络 read 到达，半截 `data:` 行先累积 | 帧拼完整即回调消费（解析器内部缓存，无显式清空） | §4 |
| 2. 事件累积 | 结构化事件进入 StreamManager（累积贯穿整条流） | 同 macrotask 的事件合并为**一次** React 通知 | §5 |
| 3. 缺口恢复游标（sessionStorage） | gap 后 `resume` 成功 → `rememberReconnectRun` 写入 | 收到 gap 先清旧游标；终态预检命中清；终态取消 409 清（均按 runId 匹配） | §6 |
| 4a. 渲染节流快照（80ms） | `isStreaming` 变 true，首个 chunk 走 leading edge 立即上屏 | 流结束置 `null` + 重置 `lastFlushRef`；组件卸载清 timer | §7.1 |
| 4b. `persistedMessages`（逐 chunk 原始数组） | submit 后每个 SSE chunk 进入 | 线程切换 / `stream_replay_gap` / 摘要捕获后置空；`finish`/`error` 后**保留**作 token 统计 baseline | §7 |
| 4c. transient bridge（摘要回退） | 检测到摘要压缩 update → 基于已提交渲染账本捕获 | 规范历史追上后**逐条** `pruneConfirmedTransientMessages`；线程切换 / gap 全量清 | §7.2 |
| 4d. 乐观消息 | `sendMessage` / `submitPreparedReplay` 时入列 | 服务器 human 消息到达 / 身份全部确认 / 上传失败或 stop / gap / 线程切换 | §7.4 |
| 4e. 历史分页（`useThreadHistory`） | infinite query 加载 | 按 threadId 隔离，切线程即换缓冲；query 失效重建 | §7.3 |
| 5. Streamdown 增量解析 | 合并后的消息进入渲染器 | 动画结束（`isAnimating` 翻转）后释放 | §8 |

**两条并行消息流**（贯穿全程，最容易踩坑）：`persistedMessages`（逐 chunk、未节流）喂 token 统计与生命周期逻辑；`renderMessages`（80ms 快照）喂渲染。**两者生命周期独立**——流结束时快照即丢，但原始数组保留到下次 submit 前（SDK 保留该 run 的 transient 事件顺序，供 `restoreLocalTurnMessageOrder` 等逻辑使用）。

## 2. 一句话结论

**前端没有"一个"流式缓冲区，而是 5 层分工明确的缓冲**，每一层对应一个故障模式：

| 层 | 位置 | 解决什么 | 缓冲介质 |
| --- | --- | --- | --- |
| 1. 字节级解析缓冲 | SDK 内部（eventsource-parser） | 网络粘包/半包 | 解析器内部缓存 |
| 2. 事件累积 + 同 tick 合并 | SDK StreamManager | 每 token 触发一次 React 通知 | StreamManager 内部数组 |
| 3. 缺口恢复缓冲 | `core/api/api-client.ts` | 服务端有界缓冲被裁剪后的断线 | 生成器 + sessionStorage 游标 |
| 4. 渲染合并缓冲 | `core/threads/hooks.ts` | 每 token 全量重渲染；摘要压缩瞬移消息 | 80ms 快照 + transient bridge ref |
| 5. 流式 markdown | `core/streamdown/` | 增量文本的增量解析与动画 | Streamdown 渲染器 |

核心实现集中在两个文件：

- **`core/api/api-client.ts`** —— 传输层包装（gap 恢复、终态预检、CSRF）
- **`core/threads/hooks.ts`** —— 消费与合并层（节流、摘要回退、三路合并）

## 3. 全链路图（前端视角）

```
SSE 字节流
  │
  ▼  [1] eventsource-parser：按 \n\n 切帧、拼半包（SDK 内部）
  │
  ▼  [2] StreamManager 累积 + throttle:true（同 macrotask 合并，SDK 内部）
  │
  ▼  [3] api-client.ts（DeerFlow 特有的传输包装）
  │      ├─ event: gap ──► 校验 run_id ──► 发 custom: stream_replay_gap 通知 hook
  │      │                  └─► threads.getState() 重载持久状态 ──► resume(lastEventId)
  │      ├─ 终态预检 shouldSkipReconnect（避免挂死）
  │      └─ store-only run 409 短路
  │
  ▼  useStream hook（useThreadStream，hooks.ts）
  │      onUpdateEvent: 检测摘要压缩 ──► 救援消息进 transientHistoryBridgeRef
  │
  ▼  persistedMessages（逐 chunk 原始数组 —— token 统计消费这一份）
  │
  ▼  [4] useCoalescedStreamMessages（80ms 快照 —— 渲染消费这一份）
  │
  ▼  mergeMessages(history, 快照, optimistic) ──► 顺序修复 ──► mergedMessages
  │
  ▼  [5] Streamdown 流式 markdown（isAnimating 动画）
  │
  ▼  UI 帧（renderedMessageSnapshotRef 记账）
```

**两条并行的消息流**（容易踩坑）：`persistedMessages`（逐 chunk、未节流）喂给 token 统计/生命周期逻辑；`renderMessages`（80ms 快照）喂给渲染。两者互不干扰。

## 4. 第 1 层：字节级解析缓冲（SDK 内部）

前端不手写 fetch reader，`useStream` 来自 `@langchain/langgraph-sdk/react`，其内部用 `eventsource-parser`（pnpm-lock 锁 3.x）做 wire 解析：

- 把网络字节流按 SSE 规范缓存
- **以空行 `\n\n` 为帧分隔符切帧**
- 分块到达的**半截 `data:` 行先累积，拼完整后才回调**出结构化事件

这一层解决的是**粘包/半包**问题——一次网络 read 可能含多帧或只有半帧，解析器负责攒齐。

---

## 5. 第 2 层：SDK StreamManager 事件累积 + 同 tick 合并

SDK 的 `StreamManager` 在解析器之上再攒一层：累积所有事件、维护 `messages` getter，并提供 throttle 合并。

`useThreadStream` 调用 `useStream` 时**显式开启 `throttle: true`**，`hooks.ts` 里的注释是重要设计决策：

```ts
// Batch stream updates received in the same macrotask without adding a
// fixed debounce interval that could delay a continuously active stream.
// Coalesce same-tick stream events into one React notification. Only the
// boolean tier is safe: the SDK's numeric tier is a trailing debounce that
// starves UI updates while chunks keep arriving faster than the window.
// Keep explicit: SDK types claim @default true, but runtime uses throttle ?? false.
throttle: true, /ˈθrɒtl/
```

要点：

- **boolean tier** = 同一 macrotask 内到达的事件合并成一次 React 通知
- **numeric tier 刻意不用**：它是 trailing debounce，chunk 到达速度快于窗口时 UI 更新会被饿死
- 显式传 `true` 是因为 SDK 类型声称默认开启、但运行时实际是 `throttle ?? false`

## 6. 第 3 层：缺口恢复缓冲（api-client.ts）

这是 DeerFlow 前端最有特色的一层。`createCompatibleClient` 用 monkey-patch 包住 SDK 的 `runs.stream` / `runs.joinStream` / `runs.cancel`，核心是 `recoverStreamReplayGaps` 生成器。

### 6.1 触发场景

后端 `StreamBridge` 是有界缓冲（默认 256 条事件）。断线重连时，如果请求的 `Last-Event-ID` 已经低于缓冲水位线，服务端不静默部分重放，而是发 `event: gap` 让客户端自选恢复——因为对 UI 来说，缺一段的假"完整"比显式断点更危险。

### 6.2 恢复流程

```ts
for await (const entry of stream) {
  if (entry.event === "gap") { gap = parseStreamReplayGap(entry.data); break; }
  yield entry;
}

// 收到 gap 后：
// 1. 校验 gap.run_id === 当前 run（不匹配直接抛错）
// 2. 超过 MAX_STREAM_GAP_RECOVERIES(=5) 次 → 抛 StreamReplayGapError
// 3. yield { event: "custom", data: { type: "stream_replay_gap", ...gap } }  → 通知 hook 清空本地流状态
// 4. client.threads.getState() 重载持久状态 → yield { event: "values", ... }
// 5. resume(runId, gap.latest_available_event_id)  → 用服务端保留窗口的【尾巴】续读
```

关键点：

- **恢复游标 = `latest_available_event_id`**（服务端保留窗口的尾巴），保证只补缺、不重复
- **预算 = 5 次**（原流不计入，所以最多消耗 6 条流）；超限抛 `StreamReplayGapError`
- SDK 本会忽略未知的 `gap` 事件并按正常结束处理，所以这里**主动转换成 `custom: stream_replay_gap`** 控制事件

### 6.3 配套的短路/预检（防止"缓冲已失效"卡死 UI）

| 函数 | 作用 |
| --- | --- |
| `shouldSkipReconnect` | `joinStream` 前查 run 状态；`success/error/timeout/interrupted` 终态直接跳过。否则会**挂在已被回收的空 bridge 上，`isLoading` 永远 true，提交按钮变成停止按钮**（注释点名的经典 bug） |
| `handleInactiveRunStream` | 吞掉 store-only run 的 409（`"not active on this worker, cannot be streamed"`） |
| `isRunNotCancellableError` | 终态取消的 409（`"is not cancellable"`）视为 no-op，清掉过期重连键；`"not active ... cannot be cancelled"` 分支**故意不匹配**（那是真实失败，必须可见） |
| `rememberReconnectRun` / `clearReconnectRun` | `sessionStorage` 的 `lg:stream:{threadId}` 记录待重连的 run，页面刷新后可续 |
| `sanitizeRunStreamOptions` | streamMode 白名单（`values/messages-tuple/updates/debug/tasks/checkpoints/custom`），丢弃后端不支持的 `streamResumable` |

## 7. 第 4 层：渲染合并缓冲（hooks.ts）

`useThreadStream` 里三条消息来源——`history`（分页持久历史）、`thread.messages`（SDK 实时流）、`optimisticMessages`（乐观消息）——先各自缓冲再合并。

### 7.1 渲染节流：`useCoalescedStreamMessages`

常量 `STREAM_RENDER_COALESCE_MS = 80`（第 1184 行）。核心是 `decideCoalesce`：

```ts
export function decideCoalesce(
  nowMs: number,
  lastFlushMs: number,
  intervalMs: number,
  hasPendingTimer: boolean,
): CoalesceDecision {
  if (nowMs - lastFlushMs >= intervalMs) {
    return { action: "flush-now" };          // leading edge：满一个间隔立即刷
  }
  if (hasPendingTimer) {
    return { action: "wait" };               // 已有 timer，不再叠加
  }
  return { action: "schedule", delayMs: intervalMs - (nowMs - lastFlushMs) };  // 单个 trailing timer
}
```

设计要点（代码注释原文语义）：

- **leading edge + 单个 trailing timer，不是 debounce**——"a dense stream can never starve rendering"
- `snapshot` 为 `null` 表示"不属于当前流"：流一结束就置 null（并重置 `lastFlushRef` 为 `-Infinity`），**防止上一个线程的快照串到新线程**；每个流的第一帧总是走 leading edge
- `sameMessageArray` 浅比较：SDK getter 每次会 mint 新数组，identity 变了内容没变时**不得触发 setState**，否则 effect 会 setState 循环
- `lastFlushRef` 用单调时钟 `performance.now()`：NTP 跳变/休眠唤醒导致的墙钟步进不会把剩余间隔拉长
- timer 触发时**重新读时钟**作为新间隔起点：timer 在主线程繁忙时会晚触发，必须从真实 flush 时刻起算

### 7.2 摘要回退缓冲：`transientHistoryBridgeRef`

背景（`#3825`）：上下文摘要中间件发出 `RemoveMessage(ALL)` + 隐藏摘要 + 保留尾部时，所有 live 消息被后端移除，而规范历史（journal 页）还没刷新到位——**用户刚看到的消息会瞬间消失**。

机制（第 1930 行起）：

1. `onUpdateEvent` 里用 `getSummarizationMiddlewareMessages` 识别 `SummarizationMiddleware.before_model` / `DeerFlowSummarizationMiddleware.before_model` 的 update
2. `computeSummarizationTransientMessages` 算出"即将被移除但用户已看到"的消息（基于**已提交渲染账本** `renderedMessageSnapshotRef`，而非当前 may-be-stale 的数组）
3. `mergeTransientHistoryBridge` 存入 `transientHistoryBridgeRef`（消息对象）+ `mergeTransientHistoryBridgeOrder` 维护 `transientHistoryOrderRef`（身份顺序锚）
4. 规范历史追上来后，`pruneConfirmedTransientMessages` **逐条释放**（identity 已在历史中出现即删除），保证 bridge 是"暂态桥"而不是第二持久源
5. `resolveTransientHistoryBridge` 用 identity-anchor 织入法把救回的消息插到正确位置（而非盲目追加到尾部），并有"未加载分页前缀不可信"的保护

配套状态：

| Ref | 作用 |
| --- | --- |
| `transientHistoryBridgeRef` | 救回的消息对象（渲染用） |
| `transientHistoryOrderRef` | 完整 identity 顺序（非渲染锚点，分页锚定用） |
| `transientHistoryThreadIdRef` | 绑定线程，防止跨线程串桥 |
| `renderedMessageSnapshotRef` | **run 级已提交渲染账本**：多次滚动压缩窗口之间兜底，regenerate 显式替换的消息不复活 |

### 7.3 历史分页缓冲：`useThreadHistory`

- TanStack infinite query，游标为 `seq`（线程全局单调序号），最新在前
- `reconcileThreadHistoryRows`：**保留本端已加载的行**——后台刷新重算所有页时，尚未加载的老页不会被"挤掉"；刷新副本按 seq 排序但不挪动既有位置
- `flattenThreadHistoryPages`：翻页展平 + 按 `run_id + identity` 去重

### 7.4 消息合并管线（`mergedMessages` memo）

```ts
resolveThreadTransientHistoryBridge(visibleHistory, transientBridge, ...) // ① 先插回救回的消息
  → mergeMessages(effectiveHistory, renderMessages, visibleOptimistic)   // ② 三源合并：实时覆盖持久
  → restoreLocalTurnMessageOrder / restoreReconnectedTurnMessageOrder     // ③ 修复用户输入顺序
```

- `restoreLocalTurnMessageOrder`：`messages-tuple` 的 AI/tool 步骤可能先于 `values` 里的用户消息到达，把可见 pending 段挪到该 turn 的用户输入之后
- `restoreReconnectedTurnMessageOrder`（刷新后的对偶逻辑）：本地 baseline 为空时，用 **"same-run sandwich" 规则**判定乱序——某 run 的可见步骤夹在"最后一个可见 human 之上、同 run 消息之下"即证明错位，只搬移最后一个终止性 AI 回复之后的步骤

## 8. 第 5 层：流式 markdown 渲染（Streamdown）

`core/streamdown/`（`components.tsx` / `preprocess.ts` / `plugins.ts` / `safe-children.ts`）封装 Streamdown 渲染器：

- `SafeMessageResponse` 的注释强调：动画生命周期依赖 `isAnimating` / `animated` 属性变化，所以 wrapper 必须放在 registry 生成的 memo 组件**之外**（那个组件只按 children memo）

## 9. 设计权衡总结

| 决策 | 原因 |
| --- | --- |
| gap 时重载持久状态，而非静默部分重放 | 缺一段的假"完整"比显式断点更危险（与后端 StreamBridge 的 `StreamGap` 语义呼应） |
| 不用 debounce / SDK numeric throttle | trailing debounce 会让持续活跃的流饿死 UI 更新 |
| token 统计走原始数组，渲染走 80ms 快照 | 统计要逐 token 准确，渲染要帧预算 |
| bridge 消息逐条释放（`pruneConfirmedTransientMessages`） | 保持 bridge 是暂态桥；否则陈旧副本会复活被过滤（superseded/regenerated）的消息 |
| 节流快照随流结束即丢（null） | 防止上一个线程的快照串到新线程（chat 页刻意不重挂载） |
| 终态 run 预检跳过 join | 避免挂在已回收的 bridge 上，`isLoading` 永远 true |
