# 流式渲染与断线容错 —— 面试稿（讲述 + 代码双版本）

> 每块两个版本：
> 【怎么讲】—— 直接说出口的口语段落，背熟。
> 【具体怎么做】—— 真实代码/机制，面试官问"怎么实现的"就答这里。
> 代码全部来自仓库真实实现，函数名、文件路径都对得上。

---

## 开场白（30 秒）

> 产品是 AI 聊天，回答是一个字一个字流回来的，一秒几十个片段。逐片段刷新
> 页面会卡、会抖。我做了两件事：**渲染侧节流 + 消息按身份合并**，让页面
> 按帧更新、历史不重排不抖动；**消息分级渲染 + 断线容错**，推理和工具调用
> 收进处理面板、结论独立气泡，断线重连后不丢不重。两块都能展开讲。

## 第一块：80ms 合并节流 —— 让页面不卡

### 【怎么讲】

> 流式片段太密，我加了个 80ms 窗口：窗口内不管来多少片段，最多真正刷新一次。
> 关键不是"定时刷"，而是**该等就等、等太久立刻上**——满 80ms 新内容马上
> 上屏，没满就挂个定时器补一帧。如果是普通防抖，高频输入会被一直推迟，
> 页面饿死在旧内容上。
>
> 还有个分层：**渲染节流，统计不节流**——token 计数吃原始逐片段数据、
> 实时跳，只有上屏的消息列表是 80ms 一帧。

### 【具体怎么做】

```ts
// frontend/src/core/threads/hooks.ts —— 纯函数，好测试
function decideCoalesce(nowMs, lastFlushMs, intervalMs, trailingPending) {
  if (nowMs - lastFlushMs >= intervalMs) return { action: "flush-now" };  // 立刻上屏
  if (trailingPending) return { action: "wait" };                          // 已有定时器，别重复挂
  return { action: "schedule", delayMs: 剩余时间 };                       // 挂一个尾缘定时器
}
```

- 时钟用 `performance.now()`（单调时钟），NTP 校时、休眠唤醒不影响；
- 每轮流从"无穷远"播种，新 run 第一个片段永不延迟；
- 流结束清空快照，防止上一个线程的残留被误画；
- 发布前浅比较，SDK 每次给新数组引用，不比较会死循环 setState。

### 【可能被追问】

- **为什么不用 rAF？** rAF 16ms 一帧太密，且后台标签页会暂停、恢复时突刺；
  80ms 是给主线程的帧预算。
- **为什么 80ms？** 约 12 帧/秒，聊天场景够用；逐 token 重跑"合并→分组→渲染"
  才是卡顿源头。
- **会不会丢消息？** 不会，节流只合批渲染，消息一条不少。
- **测试有吗？** 有，`frontend/tests/unit/core/threads/coalesce.test.ts`，
  覆盖三种动作和边界，还有帧尺度断言。

## 第二块：消息身份锚点合并 —— 历史不重排不抖动

### 【怎么讲】

> 屏幕消息来自三处：**分页历史、实时流、乐观回显**（发送中的临时显示）。
> 三者会重叠，必须去重合并。判断"同一条"用消息身份：工具消息用工具调用 ID，
> 其他用消息 ID。
>
> 合并原则：**已上屏的历史像钉子钉在原地**——有新版就原位替换，新消息插到
> 最近的钉子前面。历史位置永不动，所以滚动稳定、不跳字。
>
> 如果偷懒做"同一条只留最后一份"的全局去重，早期用户输入会被拖到列表尾部
> ——钉子方案就是防这个的。

### 【具体怎么做】

```ts
// 身份：工具消息用 tool_call_id，普通消息用 message.id
if (message.tool_call_id) return `tool:${message.tool_call_id}`;
if (message.id) return `message:${message.id}`;
// 特例：后端把用户消息替换成 隐藏System + 新Human(id 带 __user 尾缀)，
// 比较前先剥掉 __user，否则同一条会被当成两条。
```

- 历史对账（`reconcileThreadHistoryRows`）：按 `(run_id, 身份)` 去重、
  按后端持久化的单调序号 **seq** 排序——序号天生不重不乱，且**历史永不移动位置**；
- 两种顺序竞态各有一个修复函数：
  - `restoreLocalTurnMessageOrder`：新轮次的 AI/工具步骤可能比该轮用户消息
    **先到**（messages-tuple 先于 values），把跑到用户消息上面的步骤移下来；
  - `restoreReconnectedTurnMessageOrder`：刷新重放可能**丢了用户消息**，
    拿持久化历史当基准，检测"同一条 run 的消息一条在上面、一条在下面"的
    三明治，证明上面那条放错了。

### 【可能被追问】

- **乐观消息和真实消息怎么区分？** 乐观消息是本地对象，后端确认后由
  `mergeMessages` 用身份锚点替换成真实消息。
- **重连后顺序错了靠什么修？** 上面两个函数，基准都是"持久化历史是
  ground truth"。
- **摘要清空怎么办？** 后端清空消息做摘要时，有一个瞬态桥把用户已见的
  轮次救回来，避免 canonical 历史滞后时消息"消失"。

## 第三块：按轮次分组渲染 —— 过程与结论分开

### 【怎么讲】

> 消息按"一问一答"分轮。组里三类：**推理 + 工具调用**进处理中面板，
> **纯文本结论**独立气泡，**内部消息**（摘要、循环提醒、待办提醒）直接隐藏。
>
> 分组不只是排版：**token 统计按轮算**、**只有结论轮允许编辑/分支**、已确立
> 的轮次流式期间不再变 → React 复用 DOM，滚动稳定。

### 【具体怎么做】

```ts
// frontend/src/core/messages/utils.ts —— getMessageGroups 的六种组
type MessageGroup =
  | { type: "human" }                     // 用户消息
  | { type: "assistant:processing" }      // 处理中：推理 + 工具调用
  | { type: "assistant" }                 // 终端纯文本气泡
  | { type: "assistant:present-files" }   // 文件展示
  | { type: "assistant:clarification" }   // 澄清
  | { type: "assistant:subagent" };       // 子代理

// 隐藏名单
const HIDDEN_CONTROL_MESSAGE_NAMES = ["summary", "loop_warning",
  "todo_reminder", "todo_completion_reminder"];
```

踩过的三个边界（每个都有 issue 号，讲出来很加分）：

- **#3868**：有内容的 AI 消息成为独立气泡后，**不能再进处理面板**，
  否则推理内容画两遍；
- **#4304**：流式中的文本后续可能追加工具调用，未定论前**留在处理面板**，
  避免文字在面板和气泡之间跳；
- **#4399**：分页按事件序号截断、可能从轮次中间开始，工具结果先到而它的
  AI 消息在未加载的旧页上——孤儿工具结果**挂到最近分组保留可见**，
  而不是丢进 `console.error`。

### 【可能被追问】

- **推理会不会混进正文/复制/导出？** 不会，reasoning 单独存、单独折叠展示。

## 第四块：断线续传 + gap 对账 —— 不丢不重（重点）

### 【怎么讲】

> 断线重连走 SSE 的 `Last-Event-ID`：带着"我收到第几条"回去，从下一条继续。
> 但服务器缓存是**有上限的**（只留最近 N 条），断太久游标被删了就没法续。
> 这时服务器**不能假装没事继续推**——客户端会以为完整、其实缺一大段。
>
> 所以它先发一个 gap 信号："你要的位置太早，已删除，请重新同步完整记录，
> 然后从我还能给的地方继续跟。" 这个信号**没有结束标记、不等于断线**——
> 后端的 run 还在跑，客户端不能取消它。
>
> 客户端收到后：重拉完整历史 → 丢弃本地所有临时状态（已不可信）→ 用服务端
> 给的新位置续上 → 最多重试 5 次。丢了重新同步、重了按身份证去重。

### 【具体怎么做】

```text
// 后端（Gateway 流桥接）在"任何部分重放之前"先发：
event: gap
data: {"code":"stream_replay_gap","run_id":"...",
       "requested_event_id":"...","earliest_available_event_id":"...",
       "latest_available_event_id":"...","recovery":"reload_durable_state"}
```

- 后端：`StreamBridge`（Memory/Redis 两套实现）有界队列 `queue_maxsize`，
  只保留最近 N 条事件；游标被裁或消费者落后水位线 → 发 `gap` 帧（无 `id`、
  无 `end`）→ **不触发 `on_disconnect=cancel`，run 保持活跃**；
- 前端（`core/api/api-client.ts` 的 `recoverStreamReplayGaps`）：上游 SDK
  忽略未知事件名，所以包装层自己识别 `gap` → 清过期游标 → 发内部
  `stream_replay_gap` 事件 → 重读持久化历史 → 以 `earliest_available_event_id`
  重连 → 最多 5 次恢复重连；
- Hook 层收到事件后**原子重置**所有瞬态（乐观消息、临时缓冲、token 基线、
  子任务状态），再使历史缓存失效并提示用户。

### 【可能被追问】

- **gap 和普通断线什么区别？** 断线是连接没了；gap 是连接还在、游标超出
  保留窗口。所以 gap 不触发取消逻辑。
- **为什么缓存要有界？** 内存上界。代价是可能被裁，所以用显式 gap 兜底，
  而不是静默部分重放。
- **Redis 和 Memory 有差异吗？** 契约一致，细节不同：Redis 对畸形游标
  live-tail 新事件；空流上首次阻塞唤醒是"临时"的，要等下一次快照确认
  尾部仍在窗口内。
- **为什么最多 5 次？** 连续 gap 说明追不上或 run 异常，5 次后走失败路径，
  避免无限重连打爆后端。
- **`streamResumable` 呢？** Gateway 不接受这个选项，发请求前剥掉，SDK 只
  拿它做重连簿记；真正的续传就是 `Last-Event-ID` 游标。
